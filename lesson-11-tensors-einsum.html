Tensors & the einsum world

Every layer of a network — and every PnL report — is one line of Einstein summation.

Level US Senior undergrad → graduate FR Master 1 · ENSAE 2A

Strip the mystique first. A tensor, in this lesson, is a multi-index array of numbers; its order is how many indices it takes to address one entry — a scalar takes zero, a vector one, a matrix two, a stack of attention scores three or four. An index is just a labelled axis. Einstein summation — einsum — is the one-sentence grammar for computing with these arrays: write which index letters each input carries and which the output keeps; any letter that appears in the inputs but not the output is summed away (a summed index), and every survivor is a free index that becomes an axis of the answer. That is the whole language. We will speak it with a trading book — weights times exposures times factor returns is three einsum strings — and the same strings run every layer of a transformer.

The objects — a trading book as three arrays

Three arrays run the attribution report every risk system prints: what the book holds, how each asset loads on the risk factors, and what those factors did each day. Here: w[a], the weight of each of 3 assets (order 1); B[a,f], each asset's exposure — its regression beta from Lesson 5 — to each of 2 factors (order 2, 3×2); F[f,t], each factor's return on each of 4 days (order 2, 2×4). Contract them in the right pattern and you get who made what, when:

Read the string, not the formula: f is repeated across the inputs and missing on the right — summed away. a and t survive, so the output is a panel: per asset, per day. Contract once more, against the weights, and the asset index dies too:

  • w[a]book weights — how much of asset a you hold. One index ⇒ order-1 tensor. In the playground, a runs over 3 assets.
  • B[a,f]factor exposures — asset a's beta to factor f. The regression slopes of Lesson 5, stacked: 3 assets × 2 factors.
  • F[f,t]factor returns — factor f's move on day t. 2 factors × 4 days here; 20 × 250 at desk scale.
  • P[a,t]the attribution panel: asset a's factor PnL on day t. f contracted, a and t kept — this is the returns panel Lessons 6–7 called R.
  • p[t]the book PnL series — one number per day. Both a and f contracted. As matrices: p = wᵀBF — and the parentheses in that product are Interactive 2's whole story.

One honest footnote before the formalism. A mathematician's tensor is a multilinear object — it eats vectors and covectors and transforms predictably under change of basis (that is also what physicists mean by the word). Fix a basis in every space and its components form exactly a multi-index array. Deep-learning and NumPy "tensors" are those component arrays with the basis left implicit and never changed — so "tensor = multi-index array" is legitimate here, as long as we never pretend the array itself is basis-free.

The one rule — repeated means summed

Now the general rule, exactly. A spec einsum("s₁,s₂,…->s_out") gives each operand a string of index letters, one letter per axis; the output string lists the free indices. The semantics are nothing more than nested loops: loop over every free index to address an output cell, and inside, loop over every summed index, accumulating the product of the operands —

  • the free indices — the letters of the output string. They become the p axes of the result; p = 0 gives a scalar.
  • the summed indices — repeated in inputs, absent from the output. Each letter must have the same extent d in every operand that carries it.
  • the m-th input tensor, M of them. M = 1 already covers transpose, trace, and reductions.
  • operand m's index string with the loop values plugged in. For "af,ft->at", s₂ = (f,t) — so the factor reads F[f,t].

Five classics, one grammar — each just a different pattern of kept vs killed letters:

  • "ij,jk->ik"matrix product. j summed: Cik = Σj AijBjk — the canonical contraction.
  • "ij->ji"transpose. Nothing summed — a pure relabelling of axes.
  • "ii->"trace. One operand, its two axes forced equal and summed: Σi Aii.
  • "i,j->ij"outer product. No shared letter, so no sum — every pair survives. This is the rank-1 layer σuvᵀ of Lesson 8.
  • "bij,bjk->bik"batched matmul. b free in everything: one independent matmul per slice — the per-head shape of attention (Wing IV).

The precise statement

A tensor of order k is an element of a tensor product of k vector spaces; fixing a basis in each identifies it with its component array T[i₁,…,i_k]. For an Einstein expression einsum(s₁,…,s_M → s_out): each letter names an axis, letters shared across strings must have equal extents, the letters of s_out are free, and every letter appearing in some s_m but not in s_out is summed — the value is out[free] = Σ_summed Π_m T⁽ᵐ⁾[s_m]. The value is independent of the order in which pairwise contractions are performed (sums and products commute), but the arithmetic cost is not: for a matrix chain A₁A₂⋯A_n the cheapest parenthesization is found by dynamic programming in O(n³) time (the matrix-chain problem), while for general tensor networks choosing the optimal contraction order is NP-hard.

The cost of association — same value, different bill

Take the book-PnL string einsum("a,af,ft->t") and evaluate it as matrices: p = wᵀBF. Associativity offers two honest plans. Left-first collapses the book immediately — wᵀB is a single row of factor exposures (a·f multiplies), then that row sweeps the factor panel (f·t more). Right-first materializes the full asset-by-day attribution panel first (a·f·t multiplies — the entire three-deep loop nest) and only then contracts the weights (a·t more):

  • extents: assets, factors, trading days. The sliders reach desk scale — 500 assets × 20 factors × 250 days, one book over one trading year.
  • multiplies for (wᵀB)F. Equals f(a+t) — no term ever multiplies all three extents together.
  • multiplies for wᵀ(BF). Dominated by aft — the price of building the full a×t attribution panel you then immediately collapse.

At a = 500, f = 20, t = 250 the bills are 15,000 vs 2,625,000 multiplies — a 175× gap for exactly the same 250 output numbers, opened by nothing but parenthesis placement. If you genuinely need the per-asset panel (attribution reports do), the aft term is the price of the panel itself; paying it when you only wanted the book series is a silent bug no unit test catches, because the values agree perfectly.

The twist — one reassociation is a research field

Attention (Lesson 17) computes softmax(QKᵀ/√d)·V. The inner einsum "nd,md->nm" builds an n×n score matrix — for a 4,096-token context that intermediate alone has 4,096² = 16,777,216 entries per head — and the softmax is an entrywise nonlinearity on that full matrix (each row normalizes by its own sum), so it must exist before V can touch it: the nonlinearity blocks reassociation. Delete or kernelize the softmax — approximate it by a feature map, softmax(QKᵀ) ≈ φ(Q)φ(K)ᵀ — and the product reassociates exactly like wᵀBF did: φ(Q)·(φ(K)ᵀV) never forms the n×n matrix, and the cost falls from O(n²d) to O(nd²), a factor of n/d (= 64 here). That single associativity swap is the "linear attention" literature, and it is the reason Lesson 37's state-space models can stream a million tokens. Interactive 2's moral, sharpened: what walls you in is not the operation count — it's the intermediate you are forced to materialize.

Why this matters · volarixs

Your Cross-Matrix build is a contraction you now own: on the centred returns panel R[a,t], the cell grid is einsum("at,bt->ab") — Lesson 7's Gram matrix in one string — and pca_factors consumes exactly that "ab" output (Lesson 8 takes its SVD). Writing it this way is not cosmetic: the string names which index dies (time) and which pair survives (assets), which is precisely what a vectorized implementation needs to know.

The same grammar rolls up your book's Greeks: per-asset vega surfaces live on an (asset × scenario × tenor) grid V[a,s,k], and the desk surface is einsum("a,ask->sk") — weights in, asset index out. Whether that roll-up runs as one contraction or as a loop over assets is exactly Interactive 2's question at production scale, and the panel-you-materialize question is exactly why the per-asset attribution tensor is worth keeping only when someone reads it.
